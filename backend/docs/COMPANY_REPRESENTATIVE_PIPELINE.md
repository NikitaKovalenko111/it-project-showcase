# Представители компании: регистрация, модерация и приглашения

Согласованный сценарий для фронтенда. Все пути ниже начинаются с /api/v1.
Пользователь, его роль и компания — отдельные сущности. Связь company_members остаётся многие ко многим.
Одна форма не создаёт одновременно аккаунт и компанию. Объединённая регистрация с названием компании и ИНН отложена.

## Порядок действий

1. Первый представитель регистрирует аккаунт и запрашивает роль company_representative.
2. Администратор (модератор) одобряет запрос роли.
3. Представитель входит, создаёт компанию-черновик и отдельно отправляет её на модерацию. Администратор одобряет компанию.
4. Второй представитель регистрирует аккаунт и получает одобрение роли.
5. Первый представитель приглашает второго в свою компанию.
6. Второй получает уведомление и принимает приглашение. После принятия оба работают с одной компанией; создавать вторую компанию не требуется.

## 1. Регистрация первого и второго представителей

POST /auth/register — без авторизации:
```json
{
  "role": "company_representative",
  "full_name": "Петров Пётр Петрович",
  "username": "company_user",
  "email": "representative@example.ru",
  "password": "Example12345",
  "consent_version": "1"
}
```

username, email, password, consent_version и full_name обязательны. full_name — ФИО одной строкой до 500 символов, без обязательного разбиения на фамилию, имя и отчество. Email может быть не студенческим.
Сервер возвращает 201:
```json
{"user_id":"USER_UUID","message":"User registered successfully"}
```

Создаются users, user_consents и role_requests со статусом pending.
Роль в user_roles пока не назначена; компания и членство ещё не созданы. Токены при регистрации не выдаются.
ФИО сохраняется в аккаунте (users) и возвращается в верхнеуровневом full_name через GET /auth/me и в административном GET /users. Личный телефон пока не сохраняется. Должность можно указать позже при создании компании или приглашении.

До одобрения правильный логин/пароль возвращает 403 role_approval_pending. После отказа — 403 role_request_rejected.
Фронтенд показывает ожидание проверки, не выполняет бесконечный автоматический вход и не открывает рабочий кабинет.

## 2. Подтверждение роли модератором

Все защищённые запросы используют Authorization: Bearer <access_token> соответствующего пользователя.

Администратор получает GET /users?page=1&page_size=20.
Ответ: {items,page,page_size,total}; элементы содержат user_id, requested_role, role_request_status, roles.
Выбирать ожидающие записи requested_role=company_representative и role_request_status=pending на клиенте; серверный фильтр статуса для этого списка пока не реализован.
При большом списке учитывать все страницы, а не только первую.

PATCH /users/{user_id}/role-request:
```json
{"status":"approved"}
```
Для отказа: {"status":"rejected"}. Успех — 204 без тела. Подтверждение роли не подтверждает компанию.

## 3. Вход и выбор компании

POST /auth/login:
```json
{"login":"company_user","password":"Example12345"}
```
login — username или email. Ответ 200 содержит user_id, access_token, refresh_token, token_type.
GET /auth/me возвращает назначенные сервером роли; company_representative на фронтенде может отображаться как company.

После входа вызвать GET /companies/mine?limit=20.
Ответ: {items,next_cursor}; продолжать запросы с cursor, пока next_cursor не null.
Пустой список — нормальное состояние нового представителя. Показывать «Создать компанию» и входящие приглашения, а не ошибку.
Если компаний несколько, показывать выбор активной компании и сохранять именно company_id. Не определять права по названию и не считать первую компанию единственной.

## 4. Создание и отдельная модерация компании

Первый представитель вызывает POST /companies:
```json
{
  "full_name":"ООО «Пример»",
  "inn":"7707083893",
  "short_name":"Пример",
  "industry":"Информационные технологии",
  "description":"Разработка программного обеспечения",
  "activities":"Разработка веб-сервисов",
  "website":"https://example.ru",
  "contacts":"office@example.ru; +7 347 200-00-00",
  "position":"Руководитель разработки"
}
```
201 возвращает карточку с company_id и status=draft.
Создатель автоматически становится активным company_members с permissions=["manage_company"].
Компания и представитель имеют разные UUID. Контакты компании не являются отдельным личным профилем представителя.

ИНН обязателен сразу в POST /companies и изменяется через обычный PUT /companies/{company_id}.
Проверяются 10 или 12 цифр и контрольные разряды. Указывайте реальный ИНН своей компании.
Пустой или неверный ИНН возвращает 422 validation_failed.
Отдельный /legal удалён; КПП, ОГРН и юридический адрес больше не хранятся.
Регистрация аккаунта не принимает ИНН: он сохраняется при последующем создании компании.

POST /companies/{company_id}/submit-moderation — без тела, ответ 200, status=pending.
Администратор получает GET /companies/moderation?status=pending&limit=20 (cursor pagination).
PATCH /companies/{company_id}/moderation:
```json
{"status":"approved","comment":""}
```
200 возвращает карточку. Для отказа status=rejected, comment — замечание.
ВАЖНО: модерация компании использует status, а не decision, который применяется к кейсам.
После исправлений отклонённую компанию можно повторно отправить на проверку.
Статусы компании: draft → pending → approved либо rejected; suspended — административная блокировка.
Сохранение изменений одобренной карточки через PUT переводит её в pending.
В выбранном UX публикации доступны после approved. Проверки доступа и статуса окончательно выполняет сервер.

## 5. Приглашение второго представителя

Сначала второй представитель проходит шаги регистрации, одобрения роли и входа. Ему не нужно создавать компанию.
Для приглашения нужен его user_id (UUID). Он доступен самому пользователю в GET /auth/me и ответе регистрации.
API приглашения не принимает email или username. Общего поиска представителей по email для представителя компании сейчас нет.
До появления такого поиска фронтенд может предложить второму пользователю скопировать свой ID и передать приглашающему.
Административный GET /users нельзя использовать из кабинета представителя.

Первый представитель с manage_company вызывает POST /companies/{company_id}/member-invitations:
```json
{"user_id":"SECOND_USER_UUID","position":"Менеджер проектов"}
```
Успех — 201:
```json
{
  "invitation_id":"INVITATION_UUID",
  "company_id":"COMPANY_UUID",
  "company_name":"ООО «Пример»",
  "invited_by":"FIRST_USER_UUID",
  "user_id":"SECOND_USER_UUID",
  "position":"Менеджер проектов",
  "permissions":["manage_company"],
  "status":"pending"
}
```
Также ответ содержит created_at и responded_at. Permissions назначает сервер, поле не задаётся клиентом.
Текущее приглашение предоставляет полное manage_company, а не только просмотр.
Нельзя приглашать себя или уже активного участника. Для одной пары компания/пользователь может существовать только одно pending-приглашение.

## 6. Уведомление и принятие приглашения

При создании приглашения БД автоматически создаёт получателю уведомление:
```json
{
  "type":"company_member_invitation",
  "title":"Приглашение в компанию",
  "body":"Вас пригласили стать представителем компании",
  "resource_type":"company_member_invitation",
  "resource_id":"INVITATION_UUID"
}
```
Это поля уведомления; полный ответ также содержит notification_id, created_at и другие служебные поля.
resource_id — ID приглашения, не company_id и не notification_id.

Получать уведомления через GET /notifications?limit=20 и SSE GET /notifications/stream.
Для SSE нужен Bearer-заголовок; встроенный EventSource не позволяет задать его напрямую — использовать fetch-поток или подходящий клиент.
Список входящих приглашений: GET /company-member-invitations?status=pending&limit=20.
Ответ: {items,next_cursor}. Фильтр по умолчанию pending; также accepted, declined, revoked.
Отдельного GET приглашения по ID нет: карточку брать из списка. При необходимости пройти страницы.
Уведомление — сигнал; актуальные status, company_name, position и права брать из приглашения, не из текста уведомления.

Второй представитель вызывает PATCH /company-member-invitations/{invitation_id}:
```json
{"status":"accepted"}
```
Для отказа: {"status":"declined"}. Успех — 200 с карточкой КОМПАНИИ, а не приглашения.
Сервер проверяет, что приглашение адресовано текущему пользователю и ещё pending.
accepted создаёт или восстанавливает активную связь company_members, переносит должность и permissions; declined не создаёт членство.
После ответа обновить список приглашений и GET /companies/mine, выбрать присоединённую компанию.
Повторная обработка уже отвеченного приглашения возвращает 422 invalid_status — обновить список и показать актуальное состояние.

Отметить уведомление прочитанным отдельно: PATCH /notifications/{notification_id}/read.
Прочтение уведомления само по себе не принимает приглашение; принятие не помечает уведомление прочитанным автоматически.
Обратное уведомление отправителю о принятии/отказе и текстовые ответы на уведомления пока не реализованы.
Для отправки email создаётся запись в email_outbox; фактическая доставка требует настроенного email-воркера/SMTP. Наличие уведомления на сайте не гарантирует письмо.

## Границы текущей реализации

- Согласованный порядок закреплён проверками backend. Структура БД и связь многие ко многим сохранены.
- При отправке и принятии сервер проверяет активный аккаунт, назначенную роль company_representative и approved-запрос этой роли в role_requests. При отсутствии хотя бы одного условия — 403 representative_approval_required. Принятие не назначает роль. Проверки выполняются в транзакции с блокировкой пользователя, согласованной с модерацией роли, сменой роли и блокировкой аккаунта. Старые роли без записи об одобрении не проходят эту проверку; автоматически подтверждать их нельзя.
- Для отправки и принятия приглашения компания должна быть approved. При смене статуса компании уже созданное приглашение не даёт обхода проверки.
- Списка представителей компании, исходящих приглашений и поиска получателя по email для кабинета компании отдельными маршрутами сейчас нет. Не выдавать фронтенду административные права для обхода этого ограничения.
- Не обещать уведомления модератору о новой роли, пользователю об одобрении роли или компании: для этих событий в текущей реализации отдельные автоматические уведомления не подтверждены. Модератор использует очереди; пользователь повторяет вход или обновляет состояние компании.
- ФИО сохраняется при регистрации представителя; личный телефон не сохраняется. Объединённая форма регистрации компании с реквизитами отложена.

## Ошибки, которые обрабатывает фронтенд

| Запрос | Ответ / действие |
| --- | --- |
| Регистрация | 409 username_taken / email_taken; 422 validation_failed с деталями |
| Вход до проверки / после отказа | 403 role_approval_pending / role_request_rejected |
| Подтверждение отсутствующего pending-запроса роли | 404 pending_role_request_not_found |
| Отправка приглашения | 403 representative_approval_required при неподтверждённой роли или неактивном аккаунте получателя; 404 company_not_found при недоступной/неодобренной компании или существующем членстве; 422 validation_failed при неверных UUID/самоприглашении |
| Дублирующее pending-приглашение | Текущий общий маппинг возвращает 409 company_name_taken; это неточный код для этого маршрута, показывать нейтральное сообщение и не считать его проверкой названия компании |
| Ответ не адресата / неизвестное приглашение | 404 company_not_found (текущий общий код группы) |
| Принятие после изменения роли/блокировки | 403 representative_approval_required; приглашение остаётся pending и членство не создаётся |
| Принятие в неодобренную/заблокированную компанию или повторный ответ | 422 invalid_status |
| Любой защищённый запрос | 401 — обновление токенов или повторный вход; 403 — нет требуемой роли/доступа |

При изменении статуса приглашения на другом устройстве перезагружать список. Не считать показанное ранее уведомление гарантией, что приглашение ещё pending.


## Опыт и темы помощи представителя

Добавлены два необязательных текстовых поля:
- experience_and_interests — «Опыт и интересы», до 4000 символов.
- help_topics — «Темы, с которыми могу помочь», до 2000 символов.

Они хранятся в аккаунте пользователя, а не в компании; миграция 000032_representative_profile.
Изначально оба поля пустые. Это строки, не массивы тегов. При регистрации заполнять их не требуется.
Поля возвращаются в /auth/me. Чтение и редактирование отдельно:
- GET /api/v1/users/me/representative-profile
- PATCH /api/v1/users/me/representative-profile

Оба запроса требуют Bearer access token с ролью company_representative; работа идёт только с собственным активным аккаунтом.
Пример PATCH:
```json
{
  "experience_and_interests":"Разрабатываю сервисы на Go, интересуюсь базами данных",
  "help_topics":"Go, PostgreSQL, архитектура"
}
```
Ответ 200:
```json
{
  "user_id":"UUID текущего пользователя",
  "experience_and_interests":"Разрабатываю сервисы на Go, интересуюсь базами данных",
  "help_topics":"Go, PostgreSQL, архитектура"
}
```
PATCH можно отправить с одним полем: второе не изменится. Пропущенное поле или null означает «не менять»; "" очищает.
Пробелы по краям удаляются, переносы строк сохраняются. {} или только null и превышение лимита возвращают 422 invalid_representative_profile.
Неизвестные поля — 400 invalid_request. user_id не принимается, поэтому передать чужой ID для обновления нельзя.

Для фронтенда: заменить локальное сохранение этих двух полей загрузкой с сервера и PATCH.
Эта правка не добавляет редактирование ФИО или должности. full_name уже хранится в аккаунте, position относится к конкретной компании.
Публичный список наставников/представителей и публикация этих текстов этой правкой не добавляются.
