## QA фронтенда от 10.11.2026

- В деморежиме причина блокировки сохраняется в журнале. Живой `PATCH /users/{id}/status` по-прежнему принимает только статус, поэтому поле причины в живой форме скрыто.
- Форма создания команды ограничивает название 80 символами. Текущий серверный `POST /teams` принимает до 200 Unicode-символов. Карточки поддерживают и существующие длинные названия.
- Стажировки, практики и обращения в деморежиме сохраняются в браузере. Для живой модерации действует существующий контракт из таблицы выше. В частности, блокировка закрытых программ и постоянная выдача скрытых программ доступны в деморежиме, а для живого режима требуют доработки API.

## Уточнение прав и редактирование кейсов администратором — 24 ноября 2026

Согласованные роли: `admin` — модератор, `university_staff` — сотрудник УУНиТ, `company_representative` — представитель компании, `student` — студент.

### Что изменить во фронтенде

1. Добавить администратору кнопку редактирования чужого кейса, хакатона или олимпиады в статусах `draft`, `revision`, `published`. Для сотрудника УУНиТ кнопки создания и редактирования кейса скрыты.
2. Для загрузки полной формы использовать `GET /api/v1/cases/{case_id}/manage`. Публичная карточка может содержать неполный набор материалов.
3. Сохранять форму через `PUT /api/v1/cases/{case_id}`. Передавать исходный `company_id`. Полное сохранение включает актуальные массивы связей, критериев и файлов. Существующие вложения сохраняются передачей их `file_id`, даже если их загрузил представитель компании. Новый файл администратор предварительно загружает через `POST /api/v1/files`.
4. После сохранения использовать статус и версию из ответа сервера. Изменение опубликованного кейса переводит его в `revision`; повторная отправка на проверку выполняется через `POST /cases/{case_id}/submit-moderation`. Неизменяемые после черновика критерии сохранять в исходном виде.
5. Для этапов, порядка, общего плана, обложки, NDA и сроков доступны существующие маршруты. Кнопки администратора используют ограничения по статусам, применяемые компанией. Для активного плана сохраняется проверка исходного снимка, переноса дедлайна и уже опубликованных итогов. Конфликты показывать пользователю с обновлением карточки.
6. Отбор студентов остаётся за компанией. Кнопки принятия и отклонения заявок на участие отображать представителю соответствующей компании. Одна роль `admin` или `university_staff` не даёт право отбора.
7. Формы подачи заявки на кейс, подтверждения командного согласия и создания студенческой публикации доступны студенту. Неподходящая роль получает `403`.
8. При проверке актуальных возможностей ориентироваться на обе проверки: роль и право на конкретный объект. Наличие роли администратора не отменяет ограничения жизненного цикла кейса.

### Что изменено на бэкенде

- Администратор может читать и редактировать чужой кейс без членства в его компании. Проверяется действующая роль `admin` в БД.
- Административный допуск добавлен к связанным настройкам кейса: контрольным точкам, общему плану, плану мероприятия, обложке, NDA и переносу сроков. Автор публикации и компания сохраняются. В аудит записывается пользователь, выполнивший изменение.
- Полное обновление сохраняет повторно переданные файлы, уже прикреплённые к этому кейсу. Передача нового чужого файла, который к кейсу не прикреплялся, отклоняется.
- Правила отбора участников остаются привязанными к представителю компании.

### Правки фотографий во фронтенде

По просьбе владельца отменены мои изменения из коммита `8a57fcb`, относящиеся к отображению изображений: компонент `StudentProjectCover`, его подключения на страницах, обложки карточек кейсов, стили `case-card__cover` и изменение маппинга `coverUrl`.

Для последующей реализации фронтендом:
- публичные фото и обложки читать по существующим маршрутам изображения;
- приватную обложку автора получать с Bearer-токеном через `GET /files/{file_id}`, а материал в очереди проверки — через соответствующий `review/files`-маршрут;
- для защищённого изображения получать Blob через API-клиент, затем отображать object URL с освобождением при размонтировании;
- выводить изображение только при наличии файла и права просмотра.
