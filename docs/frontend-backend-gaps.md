## QA фронтенда от 10.11.2026

- В деморежиме причина блокировки сохраняется в журнале. Живой `PATCH /users/{id}/status` по-прежнему принимает только статус, поэтому поле причины в живой форме скрыто.
- Форма создания команды ограничивает название 80 символами. Текущий серверный `POST /teams` принимает до 200 Unicode-символов. Карточки поддерживают и существующие длинные названия.
- Стажировки, практики и обращения в деморежиме сохраняются в браузере. Для живой модерации действует существующий контракт из таблицы выше. В частности, блокировка закрытых программ и постоянная выдача скрытых программ доступны в деморежиме, а для живого режима требуют доработки API.

## Уточнение прав и редактирование кейсов администратором — 24 ноября 2026

Согласованные роли: `admin` — модератор, `university_staff` — сотрудник УУНиТ, `company_representative` — представитель компании, `student` — студент.

### Что изменить во фронтенде

1. Добавить администратору кнопку редактирования чужого кейса, хакатона или олимпиады в статусах `draft`, `revision`, `published`. Для сотрудника УУНиТ кнопки создания и редактирования кейса скрыты.
2. Для загрузки полной формы использовать `GET /api/v1/cases/{case_id}/manage`. Публичная карточка может содержать неполный набор материалов.
3. Сохранять форму через `PUT /api/v1/cases/{case_id}`. Передавать исходный `company_id`. Полное сохранение включает актуальные массивы связей, критериев и файлов. Существующие вложения сохраняются передачей их `file_id`, даже если их загрузил представитель компании. Новый файл администратор предварительно загружает через `POST /api/v1/files`.
4. После сохранения использовать статус и версию из ответа сервера. Изменение опубликованного кейса переводит его в `revision`; повторная отправка на проверку выполняется через `POST /cases/{case_id}/submit-moderation`. Неизменяемые после черновика критерии сохранять в исходном виде.
5. Для этапов, порядка, общего плана, обложки, NDA и сроков доступны существующие маршруты. Кнопки администратора используют ограничения по статусам, применяемые компанией. Для активного плана сохраняется проверка исходного снимка, переноса дедлайна и уже опубликованных итогов. Конфликты показывать пользователю с обновлением карточки.
6. Отбор студентов остаётся за компанией. Кнопки принятия и отклонения заявок на участие отображать представителю соответствующей компании. Одна роль `admin` или `university_staff` не даёт право отбора.
7. Формы подачи заявки на кейс, подтверждения командного согласия и создания студенческой публикации доступны студенту. Неподходящая роль получает `403`.
8. При проверке актуальных возможностей ориентироваться на обе проверки: роль и право на конкретный объект. Наличие роли администратора не отменяет ограничения жизненного цикла кейса.

### Что изменено на бэкенде

- Администратор может читать и редактировать чужой кейс без членства в его компании. Проверяется действующая роль `admin` в БД.
- Административный допуск добавлен к связанным настройкам кейса: контрольным точкам, общему плану, плану мероприятия, обложке, NDA и переносу сроков. Автор публикации и компания сохраняются. В аудит записывается пользователь, выполнивший изменение.
- Полное обновление сохраняет повторно переданные файлы, уже прикреплённые к этому кейсу. Передача нового чужого файла, который к кейсу не прикреплялся, отклоняется.
- Правила отбора участников остаются привязанными к представителю компании.

По просьбе владельца отменены мои изменения из коммита `8a57fcb`, относящиеся к отображению изображений: компонент `StudentProjectCover`, его подключения на страницах, обложки карточек кейсов, стили `case-card__cover` и изменение маппинга `coverUrl`.

## Интеграция: административное редактирование, NDA и обсуждения (24.11.2026)

### Исправления сервера

- Администратор редактирует кейсы, хакатоны, олимпиады, стажировки и практики любой компании в статусах `draft`, `revision`, `published`. Автор и компания сохраняются; сохранение опубликованной записи переводит её в `revision`. Статусы проверки, закрытия и отмены не дают произвольного редактирования. Отбор участников остаётся за компанией.
- Администратор возвращает опубликованный кейс на доработку: `PATCH /cases/{case_id}/moderation`, `{"decision":"request_revision","comment":"Что исправить"}`. Комментарий обязателен. Это изменение статуса с сохранением истории, а не откат текста к предыдущей версии. Куратор не получает административное расширение.
- `POST /cases/{case_id}/nda-versions` доступен управляющему представителю или администратору в `draft` и `revision`. Для конфиденциальной записи без действующего NDA отправка на модерацию и одобрение возвращают `409 nda_version_required`. Для старой записи на модерации: вернуть на доработку, сохранить NDA, повторно отправить и одобрить.
- В рабочем обсуждении выполнения `POST /executions/{execution_id}/comments` принимает необязательный `parent_comment_id` (UUID). Ответы содержат `parent_comment_id`, у корневого сообщения — `null`. Родитель должен существовать в том же выполнении. Ответ наследует этап родителя; явно указанный другой этап отклоняется. Права доступа к обсуждению сохраняются. Для схемы нужна миграция `000028_execution_comment_replies`.
- `GET /internships/applications` — общая очередь заявок компании на стажировки и практики. Bearer-токен представителя компании обязателен. Фильтры: `company_id`, `program_id` (UUID), `kind=internship|practice`, `status=submitted|accepted|rejected|withdrawn`, `search` (подстрока названия программы или ФИ студента, до 200 символов). Пагинация: `page` и `page_size` (1–100). Ответ: `{items,page,page_size,total}`. Порядок: сначала новые, при одинаковом времени — по ID. Область ограничена компаниями, которыми пользователь управляет; чужие заявки не раскрываются. Прежние маршруты по программе и `/applications/mine` сохранены.

### Что подключить фронтенду

1. Показывать администратору редактирование чужих записей в допустимых статусах. Для кейса загружать форму через `GET /cases/{case_id}/manage`, для программы — `GET /internships/{program_id}` с Bearer-токеном. Сохранять исходный `company_id`, ID вложений и ограничения критериев. После сохранения использовать статус из ответа.
2. Для опубликованного кейса включить действие «На доработку» с обязательным комментарием и указанным PATCH-запросом.
3. Разрешить сохранение NDA в форме доработки. Ошибку `nda_version_required` показывать как необходимость добавить NDA.
4. Кнопка «Ответить» отправляет `parent_comment_id`, а не только цитату. GET по-прежнему возвращает плоскую страницу сообщений с родительскими ID; дерево строится на клиенте. Родитель может оказаться на другой странице.
5. В общей вкладке заявок использовать `GET /internships/applications` с серверными фильтрами и пагинацией вместо объединения запросов по всем программам.
6. После обновления исходников пересобрать backend; старый запущенный образ не получает исправления автоматически.

Файлы фронтенда в рамках этих исправлений не изменяются.

## Фотографии в Markdown стажировок и практик

Для отображения загруженных фото читателям программы нужны одновременно связь файла с программой и URL чтения через программу. Простая вставка /files/{file_id} не подходит: этот маршрут защищён и доступен загрузившему файл либо администратору.

Последовательность для новой программы:
1. Создать черновик: POST /api/v1/internships. Передать company_id, kind, title, summary, content_markdown и capacity. Сохранить program_id из ответа. До появления фотографий content_markdown должен содержать непустой текст.
2. Загрузить каждую фотографию: POST /api/v1/files с Authorization: Bearer <access_token>, multipart/form-data, поле file. Сохранить file_id из ответа.
3. Сформировать Markdown: ![Фото офиса](/api/v1/internships/{program_id}/files/{file_id}/content). Подставить настоящие UUID. При отдельном API-домене URL должен указывать на API, а не на origin фронтенда; нельзя повторять префикс /api/v1.
4. Сохранить программу через PUT /api/v1/internships/{program_id}. Это полное обновление: передать обязательные поля формы, content_markdown и file_ids со ВСЕМИ файлами, которые должны остаться прикреплёнными (до 30 уникальных UUID).
5. После сохранения отправить программу на модерацию через PATCH /api/v1/internships/{program_id}/status с {"status":"moderation","comment":""}.

Пример PUT (UUID демонстрационные):
```json
{
  "kind": "practice",
  "company_id": "11111111-1111-4111-8111-111111111111",
  "title": "Практика по разработке",
  "summary": "Практика в команде",
  "content_markdown": "## О программе\n\n![Фото офиса](/api/v1/internships/22222222-2222-4222-8222-222222222222/files/33333333-3333-4333-8333-333333333333/content)",
  "capacity": 5,
  "application_deadline": null,
  "file_ids": [
    "33333333-3333-4333-8333-333333333333"
  ]
}
```

file_ids — полный список связей с файлами, а не только новые фото. Поле пропущено или null — сохранить существующие связи; [] — отсоединить все. Удаление Markdown-картинки само по себе не удаляет связь; удаление ID из file_ids не переписывает Markdown. Новый файл должен принадлежать текущему пользователю; уже прикреплённый активный файл можно сохранить повторной передачей его ID. Физического удаления файла при отсоединении нет.

Доступ: опубликованная программа — без токена; активный участник компании и администратор — с токеном; куратор — с токеном для программы на модерации. Файл должен быть активным и присутствовать в file_ids программы. В остальных случаях сервер возвращает 404. Ссылка сама по себе не делает файл публичным.

Для опубликованной программы обычная Markdown-картинка работает без заголовков. Для защищённого предпросмотра Markdown-рендерер должен загрузить картинку через авторизованный API-клиент (responseType: blob), отобразить URL.createObjectURL(blob), затем освободить URL через URL.revokeObjectURL при замене или размонтировании. Обычный img не добавляет Bearer-токен из Axios. Blob URL применяется только при отображении, в content_markdown сохраняется постоянный API URL. Токен нельзя помещать в URL.

Редактирование опубликованной программы через PUT переводит её в revision: публичный доступ к файлам прекращается до повторной публикации.

## Реквизиты компании: только ИНН

Из реквизитов сохраняется только inn. КПП, ОГРН и юридический адрес удалены из модели, API и таблицы companies миграцией 000029_company_inn_only.
Название, описание, сайт и рабочие контакты остаются полями карточки.

POST /api/v1/companies и PUT /api/v1/companies/{company_id} требуют full_name и inn:
```json
{
  "full_name":"ООО «Пример»",
  "inn":"7707083893",
  "short_name":"Пример",
  "contacts":"office@example.ru",
  "position":"Руководитель разработки"
}
```
ИНН — строка из 10 или 12 цифр с корректными контрольными разрядами; пустой ИНН и все нули недопустимы.
Пробелы по краям удаляются. Пример иллюстрирует формат; для реальной компании указывать её собственный ИНН.
Проверка контрольных разрядов не подтверждает существование организации или полномочия представителя.

PUT — полное обновление карточки, передавайте остальные актуальные поля формы.
Сохранение approved-компании переводит её в pending для повторной модерации.
ИНН возвращается в поле inn карточки. Неверный или отсутствующий ИНН — 422 validation_failed.
Отдельный PATCH /companies/{company_id}/legal удалён (404); больше не передавать kpp, ogrn, legal_address.
Регистрация аккаунта представителя не изменяется: компания с ИНН создаётся после одобрения роли.
Старые компании сохраняют прежний inn, включая пустое значение; при следующем POST/PUT требуется валидный ИНН.


## ФИО представителя при регистрации

POST /api/v1/auth/register для role=company_representative принимает:
```json
{
  "role":"company_representative",
  "username":"company_user",
  "email":"representative@example.ru",
  "password":"Example12345",
  "full_name":"Петров Пётр Петрович",
  "consent_version":"1"
}
```

full_name — обязательное ФИО одной строкой, не длиннее 500 символов; пробелы по краям удаляются. Отсутствующие обязательные поля или превышение длины — 422 validation_failed с details по соответствующему полю.
В /auth/register full_name — ФИО человека, в /companies full_name — название компании. Раздельные поля студента не меняются.

ФИО хранится в users независимо от компании и возвращается через GET /auth/me в верхнеуровневом full_name.
Административный GET /users также возвращает full_name для рассмотрения запроса роли модератором.
Студенческий профиль при регистрации представителя не создаётся; ФИО не назначает роль и не отменяет проверку модератором.
Телефон представителя не добавляется. Миграция 000031 объединяет ранее сохранённое ФИО в full_name без потери данных; у аккаунтов без ФИО возвращается пустая строка.
Регистрация студента и требования к регистрации куратора сохраняются.


## Опыт и темы помощи представителя

Добавлены два необязательных текстовых поля:
- experience_and_interests — «Опыт и интересы», до 4000 символов.
- help_topics — «Темы, с которыми могу помочь», до 2000 символов.

Они хранятся в аккаунте пользователя, а не в компании; миграция 000032_representative_profile.
Изначально оба поля пустые. Это строки, не массивы тегов. При регистрации заполнять их не требуется.
Поля возвращаются в /auth/me. Чтение и редактирование отдельно:
- GET /api/v1/users/me/representative-profile
- PATCH /api/v1/users/me/representative-profile

Оба запроса требуют Bearer access token с ролью company_representative; работа идёт только с собственным активным аккаунтом.
Пример PATCH:
```json
{
  "experience_and_interests":"Разрабатываю сервисы на Go, интересуюсь базами данных",
  "help_topics":"Go, PostgreSQL, архитектура"
}
```
Ответ 200:
```json
{
  "user_id":"UUID текущего пользователя",
  "experience_and_interests":"Разрабатываю сервисы на Go, интересуюсь базами данных",
  "help_topics":"Go, PostgreSQL, архитектура"
}
```
PATCH можно отправить с одним полем: второе не изменится. Пропущенное поле или null означает «не менять»; "" очищает.
Пробелы по краям удаляются, переносы строк сохраняются. {} или только null и превышение лимита возвращают 422 invalid_representative_profile.
Неизвестные поля — 400 invalid_request. user_id не принимается, поэтому передать чужой ID для обновления нельзя.

Для фронтенда: заменить локальное сохранение этих двух полей загрузкой с сервера и PATCH.
Эта правка не добавляет редактирование ФИО или должности. full_name уже хранится в аккаунте, position относится к конкретной компании.
Публичный список наставников/представителей и публикация этих текстов этой правкой не добавляются.
