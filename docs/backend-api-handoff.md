# ТЗ на доработку API для витрины IT-проектов

Фронтенд работает с бэкендом версии `982d97a`. Коммит `dbf0d23` вернул папку `backend` к этой версии. Ниже — контракт для следующей доработки. Все пути указаны относительно `/api/v1`.

История для справки: `e2fe00e` и `506e8df` содержат отменённые реализации. Их можно использовать для просмотра прежних названий и сценариев. В требованиях отдельно отмечены предложения, которых в этих коммитах ещё не было.

### 2.1. Сохранение общего плана

Пример добавления новой точки перед существующей:

```json
{
  "previous": [
    {
      "stage_id": "81aa92af-80e7-495f-91aa-2fe3967bcf31",
      "title": "Прототип",
      "expected_result": "Рабочая демоверсия",
      "due_at": null
    }
  ],
  "stages": [
    {
      "stage_id": "",
      "title": "Подготовка",
      "expected_result": "Сценарии проверки",
      "due_at": null
    },
    {
      "stage_id": "81aa92af-80e7-495f-91aa-2fe3967bcf31",
      "title": "Прототип",
      "expected_result": "Рабочая демоверсия",
      "due_at": null
    }
  ],
  "reason": ""
}
```

- `previous` и `stages` обязательны. Пустой план передаётся массивом `[]`. До 100 элементов в каждом массиве. Для существующих точек нужен их UUID без повторов. Сервер выдаёт UUID для новых точек. `ordinal` в ответе начинается с 1 и соответствует порядку `stages`.
- После обрезки пробелов `title` обязателен, `expected_result` — до 3000 символов, `reason` — до 1000. В прежнем сервисе допускалось до 300 символов в названии. Текущая форма ограничивает ввод 150 символами.
- Редактирование доступно в статусах `draft`, `revision`, `published` и `in_progress`. Если план изменился после чтения `previous`, вернуть `409 case_plan_changed` без частичного сохранения.
- Сохранить изменения одной транзакцией. Существующие точки сохраняют ID и прогресс. Новую точку добавить в незакрытые и неотменённые выполнения. Удаление точки с прогрессом, отправленным решением, отзывом или обсуждением отклонить с `409 case_stages_locked`. План закрытого проекта или проекта с опубликованными итогами также заблокирован.
- Для переноса существующего срока после публикации нужен будущий `due_at` и непустая причина. Иначе вернуть `422 case_plan_deadline`. Каждый перенос попадает в существующий `GET /cases/{case_id}/deadline-history` с предыдущим сроком и автором. Отдельные маршруты редактирования черновика и переноса одного срока сохраняются.

### 2.2. Аватары

- При регистрации оставлять `avatar_file_id` пустым. Пользователю без фото фронтенд показывает инициалы.
- Принимать JPG, PNG и WebP. Текущая форма ограничивает изображение 2 МиБ. Проверять реальный тип содержимого. При замене сохранять новую привязку целиком, чтобы не потерять действующий аватар при ошибке записи.
- После загрузки `GET /auth/me` возвращает новый `avatar_file_id`. Фронтенд может запрашивать `GET /users/{user_id}/avatar?v={file_id}` для обновления кэша.
- Существующие `PUT /users/me/photo` и `GET /students/{student_id}/photo` сохранить. Если общего аватара ещё нет, фронтенд может использовать уже загруженное студенческое фото.

## 3. Изменения существующих маршрутов

### 3.1. Итоги и рейтинг

`GET /cases/{case_id}/leaderboard` сохраняет формат `{ "items": LeaderboardEntry[] }`. Компания-владелец и администратор видят строки для подготовки публикации. Остальные видят только опубликованные места в рамках доступа к кейсу. После отзыва публичная таблица пуста, а компания и администратор продолжают видеть оценки для повторной публикации.

`PUT /cases/{case_id}/leaderboard/placements` сохраняет вход `{ "placements": [{ "execution_id": "UUID", "place_no": 1 }] }`. Проверять, что все указанные выполнения относятся к этому кейсу, не отменены и имеют оценку. Номера мест положительные, без повторов. Возвращать `409`, если итоги ещё не готовы. Публикация и отзыв должны сериализоваться с изменениями решений и оценок, чтобы опубликованные места соответствовали оценкам.

- **Кейс и хакатон.** Для рейтинга берётся опубликованная оценка актуального итогового решения `kind=final`. Оценки отдельных этапов не считаются итоговыми. Публикация доступна после оценки всех неотменённых выполнений.
- **Олимпиада.** Использовать `event_round_submissions`. В отменённом варианте общий результат — сумма баллов и максимумов по оценённым турам, ранжирование — по сумме баллов, затем по проценту. Публикация требовала хотя бы одного оценённого результата и отсутствия сданных, но не оценённых туров у неотменённых участников. Участники без оценок не получают место. При равенстве итоговых показателей выдача должна быть стабильной.
- **Отзыв.** Снять опубликованные места. Сохранить решения, оценки, регистрации, состав команд и прогресс. Возможность исправить оценку и повторно опубликовать итоги определяется обычными правами и статусами кейса.

### 3.2. Вложения и версии решений

- `GET /executions/{execution_id}/submissions` и `GET /submissions/{submission_id}` возвращают метаданные каждого доступного вложения в `files[]`. Те же имена должны приходить в `Content-Disposition` при скачивании через `GET /submissions/{submission_id}/files/{file_id}`. Сохранить действующие проверки доступа. Прямые URL хранилища клиенту не нужны.
- В `POST /files` для материалов решений добавить MP4 и WebM, до 20 МиБ на видео. Согласовать лимит тела запроса, конфигурацию хранилища и определение MIME по содержимому. Для неподдерживаемого типа вернуть `415 unsupported_file_type`, для превышения лимита — `413 file_too_large`. Фото и скриншоты по-прежнему можно отправлять как `kind=screenshot`, видео — как `kind=attachment`. Текущая форма принимает до 30 файлов на решение. `demo_url` остаётся способом добавить внешнее видео.
- `POST /executions/{execution_id}/submissions` позволяет активному участнику обновить итоговое решение в статусе выполнения `submitted`, пока оно без опубликованной оценки и итоги кейса не опубликованы. Предыдущую версию пометить `superseded`. Новая версия этапа заменяет только решение этого этапа. В новой версии можно повторно использовать активный файл из того же выполнения, типа решения и этапа, даже если файл загрузил другой участник команды. Файлы чужих выполнений недоступны.
- `POST /submissions/{submission_id}/evaluations` может обновить оценку того же оценщика до публикации итогов. Баллы по критериям, комментарий и итоговые значения сохраняются одной транзакцией. Чужая оценка недоступна для перезаписи. Редактирование становится доступно после отзыва итогов, если это разрешено остальными правилами проекта.

### 3.3. Стажировки и практики

Оба вида используют `InternshipProgram.kind` (`internship` или `practice`).

- `GET /internships/moderation` возвращает администратору программы в статусах `moderation`, `published`, `closed` и `hidden` с текущей пагинацией. Куратор получает только очередь `moderation`. Публичный `GET /internships` по-прежнему возвращает опубликованные программы.
- `PATCH /internships/{program_id}/status` с `{ "status": "hidden", "comment": "Причина блокировки" }` доступен администратору для `published` и `closed`. Переход в `revision` или `hidden` требует непустого комментария после обрезки пробелов. Ответ — обновлённый `InternshipProgram`. Скрытая программа исчезает из публичной витрины и остаётся доступной в очереди администратора после перезагрузки.

### 3.4. Студенты, блокировки аккаунтов и аудит

- В `GET /students/search` дополнить `StudentSearchItem` полями из раздела 1. Брать группу и уровень из профиля, а `curator_id` только из назначения с `revoked_at IS NULL`. Применить одинаковую фильтрацию для курсорной выдачи и сортировки по рейтингу. Аккаунты без активного студенческого профиля или роли `student` в студенческую выдачу не попадают. Поля с назначениями возвращать с учётом прав просмотра.
- `PATCH /users/{user_id}/status` остаётся административным и возвращает `204`. Принимает прежний запрос с одним `status` и расширенный запрос `{ "status": "blocked", "reason": "Причина блокировки" }`. Для причины длиннее 1000 символов вернуть `422 invalid_reason`.
- `GET /audit-logs` сохраняет формат. Для действий авторизованных пользователей заполнять `actor_id` и `request_id` из контекста запроса. Причину блокировки сохранить в `new_data.status_reason`. Для системных событий и старых строк `actor_id` может оставаться `null`. Техническая реализация из отменённого коммита — `audit.Begin` / `audit.Exec` с передачей данных триггеру в рамках транзакции. Пароль и хеш пароля в журнал не включать.

## 5. Приёмка и подключение фронтенда

1. Компания сохраняет новый порядок точек и переносит срок. Прогресс участников остаётся привязан к прежним ID, перенос появляется в истории. Две одновременные попытки сохранения не затирают изменения. Попытка удалить точку со сданной работой не меняет план.
2. Компания и администратор публикуют итоги и отзывают их. Участники теряют доступ к опубликованной таблице после отзыва, а оценки сохраняются. Для олимпиады итоговые баллы собираются из туров. Посторонний пользователь не может публиковать или отзывать итоги.
3. Студент сдаёт решение с JPG и MP4, после повторного входа видит оригинальные имена файлов. Представитель компании видит те же файлы. Участник чужого выполнения не может скачать вложения. Новая версия этапа не заменяет решения других этапов.
4. Новый аккаунт регистрируется без аватара. Компания, куратор и администратор могут загрузить своё фото. Загруженное ранее студенческое фото остаётся доступным.
5. Администратор блокирует опубликованную стажировку и закрытую практику. Обе пропадают из витрины, если были там, и остаются видимы в очереди после перезагрузки. Блокировка аккаунта с причиной появляется в аудите с ID администратора.
6. Прямые запросы к API отклоняют регистрацию студента с посторонним доменом, недопустимый телефон или ссылку, а также одобрение публикации с истёкшим сроком. На чистой базе доступны компетенции. Студенческая выдача содержит группы и активные назначения куратора для ролей, которым они доступны.

После готовности API на фронтенде нужно подключить пакетное сохранение плана, отзыв итогов, загрузку видео и аватары для остальных ролей. Также нужно перевести админскую очередь на расширенную выдачу, подключить причину блокировки и считать сводку куратора по фактическим данным. Для уровня обучения дополнительно добавить `education_level` в маппинг `fromStudent`.

Перед внедрением миграций сверить версии в целевой базе. В отменённых коммитах `000022` наполняла компетенции, `000023` дорабатывала аудит, `000024` добавляла поле аватара. Если эти номера уже применялись, сохранить их контрольные суммы и вносить дальнейшие изменения новой миграцией. Обновить `backend/docs/openapi.yaml` вместе с реализацией.
