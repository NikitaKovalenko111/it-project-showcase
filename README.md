# Витрина ИТ-проектов

Витрина связывает студентов, компании и кураторов. Компании публикуют кейсы, хакатоны, олимпиады, стажировки и практики. Студенты откликаются, собирают команды, сдают работы и показывают собственные проекты. Кураторы следят за закреплёнными студентами, администраторы проверяют публикации и управляют доступом.

Проект поддерживает три способа просмотра. **Демостенд с PostgreSQL** подходит, чтобы быстро проверить все роли. **Основной стенд** запускается с отдельной базой для реальных данных. **Браузерные моки** включаются вручную для работы над интерфейсом.

## 1. Реализованные функции

| Раздел | Что можно сделать |
| --- | --- |
| Витрина кейсов | Просматривать опубликованные кейсы, хакатоны и олимпиады, искать по названию и применять фильтры. Карточка показывает компанию, описание, сроки, формат участия, требования, критерии, награды и доступные материалы. |
| Компании | Просматривать каталог и карточки компаний. Представитель управляет данными своей компании в пределах выданных прав. Администратор рассматривает карточки компаний и управляет их аккредитацией. |
| Заявки на кейсы | Студент подаёт индивидуальную или командную заявку в зависимости от формата кейса. Можно приложить сопроводительный текст, резюме и ссылки. Компания рассматривает заявки на свои кейсы. Студент видит статус своей заявки. |
| Команды | Студент создаёт команду, приглашает участников, принимает приглашения или откликается на открытый набор. Участники подтверждают условия командной заявки. |
| Хакатоны и олимпиады | У мероприятия есть регламент, площадка, сроки регистрации и лимит мест. В закрытом мероприятии нужен допуск по приглашению. Для олимпиады настраиваются туры, время открытия, задания и максимальные баллы. |
| Рабочее пространство | Участники видят контрольные точки, сроки, доступные материалы и обсуждения. В зависимости от этапа можно отправить текст, ссылку или файлы. Компания проверяет решения, выставляет оценки и публикует итоги. |
| Стажировки и практики | В каталоге доступны программы двух типов. Студент может подать или отозвать заявку, компания рассматривает заявки в общей очереди. Программы проходят модерацию. |
| Студенческие проекты | Студент создаёт проект, сохраняет черновик, настраивает видимость и отправляет публичную версию на модерацию. В проект можно добавить обложку, скриншоты, описание, технологии и ссылки. |
| Профиль и портфолио | Студент редактирует личные и учебные данные, загружает фото, резюме и другие файлы. Видимость портфолио и доступ к отдельным файлам проверяет сервер. В профиле доступны сведения об участии в проектах и результатах. |
| Коммуникации | Избранное, комментарии и ответы, оценки «Нравится», уведомления, приглашения, жалобы на публикации и обращения с вложениями. |
| Контроль и отчёты | Модерация компаний, публикаций, заявок на роли и обращений. Поиск студентов, сводки куратора, аналитика, предусмотренные интерфейсом выгрузки и журнал административных действий. |

### Как проходит кейс

1. Представитель компании создаёт черновик. Доступны описание, требования, критерии, размеры команд, сроки и вложения. Для конфиденциального кейса добавляется версия NDA.
2. Автор отправляет кейс на проверку. После одобрения он появляется в доступной аудитории. Автор может отозвать публикацию с проверки в предусмотренном состоянии.
3. Студент подаёт заявку. Компания принимает решение. После подтверждения участия открывается рабочее пространство.
4. Участники сдают материалы по этапам и отправляют итоговое решение. Компания проверяет работы, выставляет оценки и публикует результаты.
5. При переносе срока сохраняются предыдущая дата и причина. Участники получают уведомление.

Для хакатонов и олимпиад используется отдельная регистрация. Индивидуальная регистрация может подтвердиться сразу. Для команды сервер ждёт согласия участников с актуальными условиями. Туры олимпиады открываются по расписанию. Работа сдаётся в пределах окна тура, а оценка разбивается по заданиям.

### Как проходят модерация и публикация

Типичный путь публикации — черновик → модерация → публикация. Если нужны исправления, модератор указывает причину и возвращает запись на доработку. После исправлений автор может отправить её снова. Правила отличаются для кейсов, компаний, программ и студенческих проектов. Доступность кнопок зависит от роли, состояния записи и права управления конкретным объектом.

## 2. Роли и права

| Роль | Код в API | Основные права |
| --- | --- | --- |
| Студент | `student` | Редактирует свой профиль и портфолио. Подаёт и отзывает свои заявки, регистрируется на мероприятия, подтверждает командное согласие и NDA. Создаёт команды и свои студенческие проекты. Сдаёт работы в доступных рабочих пространствах. |
| Представитель компании | `company_representative` | Работает с компаниями, в которых состоит. При наличии права управления создаёт и редактирует публикации, приглашает студентов, рассматривает заявки своей компании, ведёт этапы, проверяет решения и публикует результаты. |
| Куратор | `university_staff` | Ищет студентов и закрепляет себя за студентом в предусмотренном сценарии. Видит доступные работы, этапы и результаты закреплённых студентов. Работает в очередях проверки публикаций в пределах прав куратора. Отбор участников остаётся за компанией. |
| Администратор | `admin` | Управляет пользователями, ролями и назначениями кураторов. Модерирует компании, публикации, жалобы и обращения, смотрит аудит. Может создавать публикации от имени одобренной компании и редактировать их в разрешённых состояниях. Отбор на кейсы и программы остаётся за соответствующей компанией. |

Гость может открыть вход и регистрацию. Часть опубликованных данных доступна через публичные маршруты API. Для входа в основные разделы веб-интерфейса нужна учётная запись.

Сервер проверяет **роль и связь с объектом**. Например, для рассмотрения заявки недостаточно быть представителем любой компании. Нужно управлять компанией, которой принадлежит публикация. Материалы выполнения доступны его участникам и другим пользователям с правом на это выполнение.

<a name="architecture"></a>

## 3. Как устроен проект

```text
Браузер → nginx или Vite → Go API
                             ├─ PostgreSQL  — записи, права, статусы, аудит
                             └─ MinIO       — фотографии, обложки и вложения
```

| Путь | Что внутри |
| --- | --- |
| `frontend/src/pages`, `frontend/src/components` | Страницы, формы, карточки, таблицы и общие компоненты. |
| `frontend/src/api`, `frontend/src/store` | Запросы к API, преобразование серверных ответов и состояние приложения. |
| `frontend/src/styles`, `frontend/public` | Оформление, адаптивная вёрстка, шрифты и статические ресурсы. |
| `backend/cmd/server` | Точка запуска API. |
| `backend/internal/transport/http` | Маршруты, проверка HTTP-запросов и ответы. |
| `backend/internal/services` | Правила регистрации, публикации, допуска, оценивания и других операций. |
| `backend/internal/storage/repositories` | Запросы к PostgreSQL, выборки и сохранение записей. |
| `backend/migrations` | Версии схемы и начальные справочники. Миграции применяются при старте API. |
| `demo/` | Отдельная конфигурация, SQL, медиа и скрипты загрузки базового и расширенного наборов. |
| `backup`, `observability`, `.github/workflows` | Резервное копирование, сбор логов и автоматизация проверок и развёртывания. |

В основном Compose работают `frontend`, `server`, `postgres`, `minio` и `backup`. В демо API называется `api`, а для nginx внутри сети доступен под именем `server`. Браузер обращается к `/api/v1` через тот же адрес, где открыт сайт.

## 5. Быстрый запуск демостенда

Нужны Git, Docker с Compose v2, запущенный Docker Engine и Node.js 22 или новее. Из корня репозитория сначала запустите контейнеры.

```bash
docker compose -f compose.demo.yaml up -d --build --wait
```

**Windows PowerShell 5.1 или PowerShell 7**

```powershell
./demo/import.ps1
```

**Bash**

```bash
bash demo/import.sh
```

Обе команды импорта загружают демоданные в PostgreSQL, а изображения и документы — в MinIO. Откройте [демосайт на порту 3006](http://127.0.0.1:3006) и [Swagger демостенда](http://127.0.0.1:3006/api/v1/docs). Прямой API доступен на порту `13006`.

| Роль | Логин |
| --- | --- |
| Студент и капитан команды | `demo.student1` |
| Студент и участник команды | `demo.student2` |
| Представитель компании | `demo.gazprom`, `demo.inoseti`, `demo.ufanet`, `demo.action`, `demo.ibs` |
| Куратор | `demo.curator` |
| Администратор | `demo.admin` |

Общий пароль демоаккаунтов — `DemoShowcase2026!`. Дополнительные аккаунты и конкретные сценарии описаны в [README демобазы](demo/README.md). Для [базового набора](demo/basic/README.md) используйте отдельный Compose-проект, поскольку логины двух наборов пересекаются.

Запустить демосервисы без загрузки тестовых записей или пересобрать образы после правок можно так.

```bash
docker compose -f compose.demo.yaml up -d --build --wait
docker compose -f compose.demo.yaml ps
```

Повторный запуск сида использует существующие записи и файлы, если они уже загружены. Для остановки с сохранением данных используйте `docker compose -f compose.demo.yaml down`. Флаг `--volumes` удаляет базу и файлы этого демостенда. Порты можно изменить переменными `SHOWCASE_DEMO_FRONTEND_PORT` и `SHOWCASE_DEMO_PORT`.

## 6. Запуск основного стенда

Используйте `docker-compose.yml` из корня проекта. При первом запуске создайте локальный `.env` из [шаблона](.env.example) и конфигурацию API. Если файлы уже настроены, пропустите команды копирования.

```bash
cp .env.example .env
cp demo/config.demo.yaml backend/config/config.yaml
```

В PowerShell вместо `cp` можно использовать `Copy-Item`. Скопированный YAML служит основой. Перед стартом измените в нём настройки основного окружения.

| Где | Что настроить |
| --- | --- |
| `.env` | Задайте `POSTGRES_PASSWORD`. Переменные `MINIO_ROOT_USER` и `MINIO_ROOT_PASSWORD` передаются сервису резервного копирования и должны совпадать с учётными данными MinIO. |
| `backend/config/config.yaml`, блок `jwt` | Задайте два разных случайных секрета для токенов доступа и обновления. Проверьте сроки действия и интервал очистки сессий. |
| Блоки `http_server` и `postgres` | В контейнере HTTP-сервер слушает `:3005`. Основной Compose задаёт PostgreSQL `postgres:5432`, пользователя и базу `showcase`, пароль из `.env`. Настройте `cors_allowed_origins`, если UI обращается к API с другого origin. |
| Блок `object_storage` | Для основного Compose используйте бакет `showcase`. Адрес и ключи API переопределяются в сервисе `server`. Для серверного развёртывания замените локальные значения MinIO согласованно в сервисах `minio`, `server` и `backup`. |
| Блок `email` | Добавьте настройки SMTP, если нужна отправка почты. Для локальной работы достаточно оставить почту выключенной. |

```bash
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
docker compose logs --tail=100 server
```

Откройте [сайт на порту 3000](http://localhost:3000) или [Swagger через фронтенд](http://localhost:3000/api/v1/docs). По умолчанию прямой API доступен на порту `3005`, MinIO API — на `9000`, консоль MinIO — на `9001`.

На новой базе рабочие каталоги заполняются реальными публикациями. Для входа зарегистрируйте студента или используйте выданную учётную запись. Первого администратора нужно назначить при подготовке окружения с участием ответственного за базу. В публичной регистрации такой роли нет.

Для сервера настройте HTTPS на внешнем прокси. Ограничьте прямой доступ к API и MinIO правилами сети или привязкой портов. Храните `.env`, YAML с секретами и копии базы отдельно от Git. Учётные данные демостенда предназначены для локальной проверки.

## 7. Разработка фронтенда и бэкенда

### Vite с работающим API

Из каталога `frontend` выполните следующие команды.

```bash
npm ci
npm run dev
```

Vite обычно открывает `localhost:3000`. Если порт занят, смотрите адрес в выводе команды. Путь `/api` проксируется на `http://127.0.0.1:3005`. Чтобы использовать демобазу, запустите демостенд и задайте в `frontend/.env` следующие параметры.

```dotenv
VITE_API_URL=/api/v1
VITE_API_PROXY_TARGET=http://127.0.0.1:13006
VITE_API_TIMEOUT_MS=15000
```

После изменения переменных перезапустите Vite. Можно взять за основу [frontend/.env.example](frontend/.env.example). Команда `npm run dev:integration` тоже использует реальный API и читает настройки режима Vite `integration`.

### Явный режим браузерных моков

```bash
npm run dev:mock
```

Этот режим загружает данные в браузер и даёт быстрый вход под тестовыми ролями. Часть данных хранится в localStorage, вложения — в IndexedDB. При обычной разработке и Docker-сборке данные приходят из API. Подробнее — в [описании браузерных моков](frontend/README-mocks.md).

### Бэкенд без контейнера API

Нужны Go версии из `backend/go.mod` и доступные с хоста PostgreSQL и MinIO. Укажите их адреса и учётные данные в `backend/config/config.yaml`. Для Go-процесса на хосте используйте адреса, доступные с хоста. Имена `postgres` и `minio` работают внутри сети Compose. База основного Compose по умолчанию доступна контейнерам, поэтому для локального Go-процесса подготовьте отдельное подключение.

```bash
cd backend
go mod download
go run ./cmd/server -config=./config/config.yaml
```

## 8. Регистрация, вход и безопасность

### Как появляется аккаунт

- Студент вводит логин, пароль, ФИО, учебные данные и подтверждает согласие на обработку персональных данных. Для саморегистрации нужна почта `@stud.uust.ru`. Сервер создаёт профиль и сохраняет версию согласия.
- Представитель компании или куратор отправляет запрос на роль. Войти под запрошенной ролью можно после решения администратора. Интерфейс сообщает о рассмотрении или отклонении.
- Компания создаётся отдельно от регистрации представителя. При создании или изменении карточки API проверяет ИНН и его контрольные цифры. Порядок работы описан в [контракте компаний](backend/docs/COMPANY_REPRESENTATIVE_PIPELINE.md).
- Логин состоит из 3–32 символов. Допустимы строчные латинские буквы, цифры, точка, дефис и подчёркивание. Пароль содержит букву и цифру, занимает от 8 до 72 байт и вводится без пробелов. Войти можно по логину или email.

### Как защищаются аккаунты и данные

| Механизм | Что делает |
| --- | --- |
| bcrypt | Хранит хеш пароля. При входе сервер сверяет пароль с хешем. |
| JWT | Токен доступа подписан HS256 и передаётся в заголовке `Authorization: Bearer ...`. Секреты доступа и обновления настраиваются отдельно. |
| Сессии | В базе хранится хеш токена обновления. При обновлении токен заменяется. При выходе соответствующая сессия отзывается. Веб-клиент хранит токены в localStorage. |
| Доступ | Сервер проверяет роль, статус аккаунта, членство, права управления, участие в выполнении и видимость ресурса. Эти правила действуют и при прямом запросе к API. |
| CORS | Для запросов с другого origin API проверяет разрешённую схему, адрес и порт. Обычный запрос с сайта проходит через прокси того же адреса. |
| Файлы и разметка | Сервер проверяет формат, размер и права на файл. Фронтенд очищает Markdown перед отображением. |
| Аудит и согласия | В PostgreSQL записываются административные действия и согласия с условиями участия и NDA. |

## 9. Данные, файлы и уведомления

- **PostgreSQL** хранит пользователей, компании, проекты, заявки, сроки, оценки, разрешения и метаданные файлов. Данные остаются в томе после обычной остановки контейнеров.
- **MinIO** хранит содержимое файлов. Открытые изображения выдаются предназначенными для этого маршрутами. Приватные резюме, решения, материалы проверки и вложения обращений выдаются после проверки прав.
- **Аватары и логотипы** загружаются по данным API. Для отсутствующих изображений интерфейс показывает инициалы или сообщение об отсутствии файла.
- **Лимиты файлов** зависят от `object_storage.max_file_size` и типа загрузки. У аватара есть предел 2 МиБ, видео MP4/WebM ограничены отдельно, к обращению можно приложить до пяти файлов по 2 МиБ. Подробнее — в [контракте загрузки](docs/upload-size-contract.md).
- **Уведомления** доступны внутри сайта. Поток SSE передаёт новые события от сервера. SMTP включается отдельно. Для отправки писем задаются хост, порт, отправитель, интервал обработки и при необходимости учётные данные SMTP.

## 10. API и тесты

Базовый путь API — `/api/v1`. Для проверки доступности используйте `GET /api/v1/system/health`. Интерактивный Swagger открыт на `/api/v1/docs`. Списки используют пагинацию по страницам или курсору. Ошибки API включают код и идентификатор запроса, который помогает найти запись в логах.

Контракты описаны в [OpenAPI](backend/docs/openapi.yaml), [справочнике API](backend/docs/API.md) и [описании сценариев интеграции](backend/docs/API_INTEGRATION_WORKFLOWS.md).

```bash
# Из frontend
npm test
npm run build

# Из backend
go vet ./...
go test ./...
go build ./...
```

Интеграционным тестам нужна отдельная PostgreSQL с применёнными миграциями. Укажите адрес в `TEST_DATABASE_URL` и настройте `search_path=showcase,public`. Переменная `TEST_DISPOSABLE_DATABASE=1` включает сценарий, который записывает тестовые данные и историю модерации. Для него используйте базу, которую можно удалить после проверки.

```bash
# Из backend, после настройки TEST_DATABASE_URL и TEST_DISPOSABLE_DATABASE
go test -tags integration ./internal/integration
```

## 11. Логи, резервные копии и развёртывание

На сервере подключитесь по SSH и перейдите в папку проекта. Для основного и демонстрационного Compose используются разные имена API-сервиса.

```bash
# Основной стенд
docker compose ps
docker compose logs --tail=100 -f server frontend
docker compose logs --since=1h backup

# Демо
docker compose -f compose.demo.yaml ps
docker compose -f compose.demo.yaml logs --tail=100 -f api frontend
```

`Ctrl+C` останавливает просмотр логов. Для контейнера по имени используйте `docker logs --tail=100 -f ИМЯ_КОНТЕЙНЕРА`. Команда `docker compose ls` показывает активные проекты и их файлы Compose.

**Резервные копии.** Основной сервис `backup` запускает скрипт в 03:00 по времени контейнера. Скрипт сохраняет дамп PostgreSQL и файлы бакета MinIO в каталог `backups/`, проверяет читаемость дампа и удаляет копии старше семи суток. Для восстановления нужны оба компонента из одного набора. Восстановление сначала проверяйте на отдельном окружении.

**Графики и поиск по логам.** В `observability` есть отдельный Compose с Alloy, Loki и Grafana. Задайте `GRAFANA_ADMIN_PASSWORD` по [шаблону](observability/.env.example), затем запустите `docker compose --env-file observability/.env -f observability/docker-compose.yaml up -d` из корня. Grafana доступна локально на порту `3001`, Loki — `3100`, Alloy — `12345`.

**GitHub Actions.** [CI](.github/workflows/ci.yaml) запускает проверки и сборку Go, сборку фронтенда и обоих Docker-образов для изменений в `develop` и `main`. [CD](.github/workflows/cd.yaml) после успешного CI на push в `main` подключается к серверу по SSH, обновляет репозиторий и пересобирает основной Compose. SSH-ключ и адрес сервера берутся из секретов GitHub.

<a name="troubleshooting"></a>

## 12. Частые проблемы

| Симптом | Что проверить |
| --- | --- |
| Демоаккаунт не входит | Откройте `127.0.0.1:3006`, проверьте результат запуска сида и ввод общего демопароля. На порту `3000` работает отдельная база основного стенда. |
| `service "api" is not running` | Проверьте контейнеры через `docker compose -f compose.demo.yaml ps` и логи `api`. В основном Compose сервис называется `server`. |
| `Origin is not allowed` | Откройте сайт по адресу фронтенда и используйте относительный `/api/v1`. Для отдельного origin добавьте его точное значение в настройки CORS и примените конфигурацию API. |
| После изменения кода видна старая версия | Пересоберите нужный Compose через `up -d --build --wait`. Для Vite проверьте адрес и перезапустите его после изменения `.env`. |
| API отвечает `502` через сайт | Посмотрите состояние контейнеров API, PostgreSQL и MinIO. Проверьте указанный в конфигурации nginx или Vite адрес API. |
| Файл не загружается | Проверьте формат, серверный лимит размера, права и состояние MinIO. Для внешнего прокси проверьте и его настройки запроса. |
| Каталоги пустые | На новой базе публикуйте записи через интерфейс. Для локальной проверки с готовыми записями используйте демосид и адрес демостенда. |
| Docker сообщает о занятом порте | Посмотрите запущенные проекты через `docker compose ls` и порты через `docker ps`. У демостенда порты задаются через `SHOWCASE_DEMO_FRONTEND_PORT` и `SHOWCASE_DEMO_PORT`. |
